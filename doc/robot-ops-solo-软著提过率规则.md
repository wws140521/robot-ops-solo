# Robot-Ops-Solo 软著提过率规则手册

> 适用版本：中国版权保护中心 **2026-03-15** 起执行的《计算机软件著作权登记》有限实质审查规则
> 适用范围：`robot-ops-solo` 项目下所有拟登记软著单元（适配器引擎 / UDM 运行时 / SOP 编排 / 健康分 / 边缘桥接 / Dashboard）
> 文档性质：内部合规规则（rules），供提交前逐条自检，不替代《软著去 AI 化指南》

## 0. 一句话总则

**2026 年软著审查 = "AI+人工双重严审"，判定核心是「功能—代码—文档」三重一致性 + 独创性真实性。** 本手册的全部规则都服务于一件事：让审查员在源码比对、文档核验、功能对照三个环节都找不到驳回理由。

> 依据：版权保护中心 2026-03-15 公告将审查从"形式审查"转向"实质审查"，启用新版申请表、功能描述 500–1300 字、代码相似度比对系统、三重一致性校验[citation:13][citation:15][citation:19][citation:24][citation:27]。

## 1. 材料清单与硬性数量规则（先卡数量，再卡质量）

软著登记申请文件 = **申请表 + 鉴别材料（源代码 + 文档）+ 身份证明**。以下为不可突破的"数量红线"[citation:12][citation:15][citation:18][citation:21]。

| 材料 | 硬性要求 | 本项目操作规则 |
|------|---------|--------------|
| **申请表** | 2026-03-15 新版，旧版系统直接不受理；经办人须为单位在职人员并手写真实性承诺 | 用官网在线填报打印，**禁止沿用往年模板**；经办人选公司真实在职人员 |
| **源代码（程序鉴别材料）** | 前 30 页 + 后 30 页共 60 页；每页 ≥50 行有效代码（不含空行/注释行凑数）；不足 60 页则提交全部；末页须为完整模块结尾 | 从主入口/主类定义连续取前 30 页，从结尾连续取后 30 页，**不得跳页挑选"漂亮片段"**；总量不足时提交全部并附《独创性说明》 |
| **文档（文档鉴别材料）** | 用户手册或设计说明书 ≥15 页（建议 15+），每页 ≥30 行，图文结合，含封面/目录/功能说明/界面截图 | 二选一：操作手册（含登录→主界面→功能跳转连续截图）或设计说明书（含架构图+流程图+模块/函数说明+算法） |
| **身份证明** | 企业：营业执照副本扫描件（加盖鲜章）；经办人身份证 + 授权书 | 扫描件清晰、平铺、无反光、无遮挡、露出四边 |

### 规则 R1.1（源码行数）
提交源码**有效代码量建议 ≥3000 行**（含注释空行前）；若真实自研代码不足 3000 行，提交全部并在说明书中强化"独立创作+功能对应"说明，**不得用空行/注释/Todo 凑数**[citation:11][citation:14][citation:16][citation:23]。

### 规则 R1.2（连续性与完整性）
源码前 30 页须从**主程序入口/主类定义或配置初始化**开始连续取；后 30 页须以**完整函数块/模块结束**收尾（如函数闭合、模块终止符）。末页不得出现断行[citation:14][citation:17][citation:20][citation:26]。

### 规则 R1.3（格式）
源码与文档均**纵向排版、文字从左向右**；统一提交 **PDF**；代码字体用等宽字体（Courier New / 宋体），字号 9–10pt、单倍行距，让代码自然铺满每页 50 行，**禁止靠放大字号/加宽行距硬凑**[citation:12][citation:18][citation:23]。

## 2. 三重一致性校验规则（2026 核心红线）

2026 年审查机制对**申请表 / 源代码 / 说明文档**三份材料实行一致性校验，**页眉、软件名称、版本号、功能描述必须完全匹配，一字不符即补正或驳回**[citation:13][citation:19][citation:24][citation:27]。

### 规则 R2.1（名称完全一致）
- 软件全称在三处**逐字一致**：申请表"软件名称"、源码每页页眉、文档每页页眉。
- 命名规范：`品牌标识 + 核心功能 + 软件/系统/平台 + V1.0`。示例：`RobotOps 跨品牌工业机器人协议适配引擎软件 V1.0`[citation:10][citation:14][citation:26]。
- **禁止**：含"中国/全国/国家"等限制性行政区域词、含知名商标/品牌近似词、含"至尊/终极"等夸大词、名称与功能无关[citation:14][citation:26]。

### 规则 R2.2（版本号完全一致）
- 三处版本号统一为 `V1.0`（首次登记强烈建议用 V1.0，后续升级再出 V2.0），大小写、标点、空格全一致[citation:14][citation:26][citation:28]。
- 源码/文档/截图内出现的版本号也必须为 `V1.0`，不得出现"v1.0 / 1.0 / Ver1.0"混用。

### 规则 R2.3（功能描述对应）
- 申请表"主要功能和技术特点"（500–1300 字）中描述的**每一个功能模块，都必须在源码中找到对应实现**；源码中体现的核心功能，也应在文档中有说明[citation:13][citation:14][citation:24]。
- 文档中截图的菜单/按钮/字段，用全局搜索在源码中至少出现 ≥1 次（对应英文/中文标识符）[citation:28]。

### 规则 R2.4（页眉页脚统一）
- 源码与文档每页页眉标注"软件全称 + 版本号"；右上角标注连续页码（源码 1–60，文档按实际）；页脚注明著作权人全称[citation:14][citation:25][citation:26]。

## 3. 功能描述（500–1300 字）撰写规则

功能描述是 2026 年审查的"重灾区"：字数不达标直接驳回，套话/空话被 AI 文本识别工具打回[citation:13][citation:15][citation:19][citation:22]。

### 规则 R3.1（字数）
严格控制在 **500–1300 字**（含研发背景/核心架构/技术实现/应用场景）。少于 500 或多于 1300 均可能被驳回[citation:13][citation:15][citation:16][citation:19]。

### 规则 R3.2（内容结构，建议照此分段）
1. **研发背景**（约 80–120 字）：说明要解决的行业痛点（如"工业机器人品牌协议孤岛，FOCAS/OPC UA/Modbus 互不通"）。
2. **面向领域/行业**（约 30–50 字）：工业机器人运维集成、工厂设备科。
3. **核心架构**（约 150–250 字）：用技术语言描述模块划分（如"适配器工厂 + 品牌注册表 + 协议解析层 + UDM 输出格式化"）。
4. **主要功能**（约 200–350 字）：按模块逐条说明（FANUC FOCAS 适配器 / KUKA OPC UA 适配器 / 埃斯顿 Modbus 适配器 / UDM 运行时 / SOP 编排引擎……）。
5. **技术特点**（约 100–200 字）：设计模式/算法/技术实现（策略模式+工厂模式、TypeScript/Python、健康分加权算法、MQTT 转发）。
6. **应用场景**（约 50–100 字）：跨品牌机器人同屏监控、预测性维护中台接入层。

### 规则 R3.3（禁止事项）
- ❌ "实现数据处理、信息展示"等**套话/空话**[citation:13][citation:24]。
- ❌ 大段描述**第三方交互模块**（API 调用、微信小程序前端交互）等非自有功能[citation:16]。
- ❌ 使用 AI 生成的空洞模板化文字（审查系统搭载文本识别工具，批量 AI 套话一眼识别）[citation:13][citation:19]。
- ✅ 聚焦**自有核心功能模块**，以"通过 XX 算法/模式实现 XX 功能"的技术逻辑为主线[citation:24]。

## 4. 源代码去 AI 化与独创性规则

2026 年新增**代码相似度比对系统**，源码与历史登记软件、开源项目全面比对，**相似度过高直接驳回**；同时核查功能描述与源码匹配度[citation:13][citation:16][citation:24][citation:27]。

### 规则 R4.1（剔除非自研代码）
提交源码中**不得出现第三方版权标识/无关项目名称**（如 `Copyright 20xx Apache/BSD/MIT` 头、其他公司名、其他开发者姓名）[citation:11][citation:14][citation:20][citation:23]。处理：`node_modules`/开源框架基础代码/自动生成 UI 布局代码**不进鉴别材料**；用到开源组件需二次开发形成独立逻辑并标注来源[citation:16][citation:24]。

### 规则 R4.2（核心业务代码优先）
提取源码时**优先提取具有业务逻辑、数据处理、核心算法的模块**（如 `adaptByBrand`、`health-score.ts`、`sop-engine`），避免大量粘贴配置文件、依赖包引入、环境配置代码[citation:14][citation:16][citation:20]。仅提交环境配置/依赖引入 → 补正[citation:19][citation:23]。

### 规则 R4.3（制造合理差异，但禁止抄袭改写）
变量/函数名采用**项目私有命名**（如拼音缩写+英文混写的项目前缀），避免在多个登记单元间大量重复连续 30 行以上代码[citation:26][citation:28]。注意：这是"体现独立创作"而非"抄袭改写他人代码"。

### 规则 R4.4（保留核心算法实现）
健康分算法、RUL 估算、告警码翻译表等**算法类核心代码必须真实存在于提交源码中**（哪怕只有几十行），并在说明书中专页贴出对应文件截图[citation:14][citation:19][citation:28]。纯 CRUD + 空壳说明"含 AI 算法" → 补正。

### 规则 R4.5（AI 辅助披露）
2026 新规要求如实披露 AI 辅助情况。**本项目规则**：AI 生成代码（如 `fanuc_mock.py`/`kuka_mock.py` 中的 mock 假数据字典）**不进入软著源码**；人工编写的核心逻辑、真实调试痕迹、手写文档进入软著材料；如使用了 AI 辅助开发，在申请材料中按官网要求如实声明人工占比[citation:13][citation:15][citation:27]。**纯 AI 生成模块不得登记**[citation:13][citation:27]。

## 5. 说明文档（用户手册/设计说明书）规则

### 规则 R5.1（操作手册，推荐本项目使用）
若选操作手册，必须：含**完整登录界面 → 主界面 → 各主要功能操作流程 → 界面跳转**的连续截图与文字说明；截图须清晰、含完整标题栏/菜单栏/功能按钮，无第三方水印/Logo[citation:14][citation:17][citation:26][citation:28]。文字不能"一行带过"，须逐图说明本截图内的按钮与功能[citation:14]。

### 规则 R5.2（设计说明书，可选）
若选设计说明书，须含：软件结构图、各功能流程图、逻辑框图，并介绍总体设计、接口设计、模块名称与功能、函数名称与功能、算法、运行设计等[citation:14][citation:21]。

### 规则 R5.3（文档与代码对应）
说明书描述的功能模块，在源码中**必须有对应实现**；可依照说明文档各模块，将对应模块代码粘贴进文档并标注模块名称与功能说明，必要时附《源程序与文档功能对应表》辅助审查[citation:14][citation:26]。

### 规则 R5.4（截图真实性）
**截图必须来自软件真实运行界面**（本项目即本地 `pnpm dev` + mosquitto + mock 脚本跑通后的 Dashboard 截图），**禁止用 AI 生成的界面图片**（审查对"图文不符/截图模糊/含外部 Logo"敏感）[citation:14][citation:17][citation:20][citation:26]。

## 6. 申请表填写规则（细节决定成败）

### 规则 R6.1（名称/版本）
见 R2.1、R2.2。名称与功能直接关联，版本号全程一致[citation:10][citation:14][citation:26]。

### 规则 R6.2（日期逻辑）
- **开发完成日期 ≤ 首次发表日期**[citation:11][citation:14][citation:26]。
- **开发完成日期 ≥ 公司（营业执照）成立日期 + 建议 ≥3 个月**（成立不到 2 个月即登记"开发完成"易被质疑真实开发周期）[citation:14][citation:20][citation:28]。
- 若真实开发完成早于公司成立，需附《前期开发说明》（写开发人员信息并加盖公章）[citation:26]。

### 规则 R6.3（开发方式/分类）
按实际情况选"独立开发/合作开发/委托开发"；合作开发需提供全体权利人签章的《合作开发协议》（签订日期不得晚于开发完成日期）；委托开发需提交委托开发合同明确权属[citation:14][citation:26]。

### 规则 R6.4（品牌关联）
软件名称含非功能属性品牌标识时，需提交《品牌与软件关联性说明》；若品牌已注册商标，需提交商标注册证复印件（加盖公章）且核定使用范围涵盖软件领域[citation:14]。

### 规则 R6.5（签章页）
申请确认签章页须 **A4 纸打印后加盖鲜章/亲笔签名，不得使用电子签章或扫描章**；扫描件清晰、平铺、无反光、无遮挡；流水号/条码清晰[citation:14][citation:17][citation:26]。

## 7. robot-ops-solo 软著单元拆分与命名规则

按"可独立运行、有自有算法、非纯 CRUD"原则拆分为多个登记单元，每个单元独立命名、独立提交。命名须符合 R2.1。

| 单元 | 建议软件全称 | 源码落点（仅示例） | 优先级 |
|------|------------|------------------|--------|
| U1 | RobotOps 跨品牌工业机器人协议适配引擎软件 V1.0 | `packages/adapter-kit/src/adapters/**` | P0 |
| U2 | RobotOps 工业机器人统一数据模型运行时软件 V1.0 | `packages/adapter-kit/src/types/unified.ts` + 转换函数 | P0 |
| U3 | RobotOps 机器人健康评分与剩余寿命预测软件 V1.0 | `ai/health-score.ts`（人工算法核心） | P0 |
| U4 | RobotOps SOP 任务编排引擎软件 V1.0 | `packages/sop-engine/**` | P1 |
| U5 | RobotOps 边缘 MQTT 遥测采集与桥接软件 V1.0 | `roboticsops-edge/*.py`（去 mock 的真实采集骨架） | P1 |
| U6 | RobotOps 机器人运维可视化 Dashboard 软件 V1.0 | `apps/web-console/src/**`（与后端数据模型绑定） | P2 |

### 规则 R7.1（单元间代码去重）
同一主体每日申请量建议控制在 **3 份以内**，避免触发批量预警[citation:24]。多单元拆分时，**各单元源码/文档不得大量重复连续代码**；如系统较大、一套系统拆 2–3 个软著，须重新整理对应说明书与代码，确保各单元独立创作[citation:26][citation:28]。

## 9. 收到补正通知的应对规则

补正是材料瑕疵的合规提示（非驳回），多数问题集中在源码格式与文档质量[citation:11][citation:14][citation:17][citation:27]。

### 规则 R9.1（按期补正）
收到补正通知后**须在规定期限内（通常 30 日内）完成修正并重新提交，逾期视为撤回**[citation:15][citation:24][citation:27]。

### 规则 R9.2（一次补到位）
看清补正项（申请表/源码/文档/权属），针对性补充，**一次补到位避免反复补正拖长周期**[citation:11]。如权属不清可补充委托合同/职务开发证明；如功能-代码不符则补《源程序与文档功能对应表》[citation:14][citation:24]。

### 规则 R9.3（临近高企节点）
若临近高企申报节点材料仍未下证，可评估走**加急通道**补救（代办加急周期约 15–20 工作日，需材料零补正）[citation:11]。

## 10. 红线禁令（一票否决级）

以下行为**直接触发驳回或纳入版权登记失信名单**，影响个人征信及企业后续申报资格[citation:13][citation:19][citation:24][citation:27]：

- ❌ 使用旧版申请表提交（系统直接不受理）
- ❌ 功能描述用 AI 批量生成套话/空话、字数不符 500–1300
- ❌ 源码与历史登记/开源项目相似度过高（未二次开发直接引用开源代码）
- ❌ 虚构功能、提交伪造/编造材料
